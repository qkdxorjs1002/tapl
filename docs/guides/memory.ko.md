# 연상 기억

[문서 홈](../README.ko.md) · [English](memory.md)

검증한 재사용 가능한 교훈을 다음 작업에서 찾아 원본을 확인하는 기능입니다. 작업 기록 전체를 기억에 복제하지 않고, 탐색에 도움이 되는 짧은 단서를 저장합니다.

## 회상 기준과 한계

`[recall] enabled = true`가 기본값입니다. `tapl_summarize_run`은 선택적으로
`recall_query`를 받고 run당 한 번 관련 있는 짧은 기억 단서를 최대 3개 제공합니다.
3개는 상한입니다. 무관한 기억으로 빈자리를 채우거나, 유효한 후보나 응답 공간이
부족한데도 3개를 보장하지 않습니다. RUN 시작의 자동 회상은 현재 로컬 RUN에서
생성했거나 해당 RUN 자체를 원본으로 가리키는 기억을 제외합니다.
Hook, status, next-action 조회에서는 기억을
검색하지 않습니다. 먼저 단서로 탐색하고 원본 item/archive를 확인하며, 부족하면
`tapl_search_history`를 사용합니다. 기억 내용은 검토할 자료이며 실행 지시가 아닙니다.

명시적인 `recall_query`는 구체적인 용어·식별자 3–8개로 간결하게 작성하세요.
검색은 앞의 어휘 토큰을 최대 8개 사용합니다. 생략하거나 빈 문자열이면 RUN 요약에도
같은 앞 8개 제한을 적용합니다. 검색에서 용어 번역, 도메인 동의어 확장, 한국어 조사
제거, 요약 뒷부분의 키워드 선택은 하지 않습니다. 키워드 목록의 대표 표현을 사용해
구체적인 질의를 작성하세요.

한국어 단서는 `연상 기억`과 `연상기억`처럼 공백만 다른 표현도 검색할 수 있습니다.
기존 검색 색인은 합친 길이가 4글자 이상인 한글 단어 구간을 개별 cue 안에서만
별칭으로 만들고 원문 cue와 note를 보존합니다. 영어·숫자·코드 식별자·문장부호 경계를
합치지 않습니다. 자동 회상은 여전히 전체 단서 일치 또는 기존의 의미 있는 단어 2개
일치 기준을 사용합니다. `기억`이나 `프로젝트` 같은 단어 하나가 더 긴 단서 전체의
일치로 인정되지는 않습니다.

후보 검색과 적격성 판단에는 DB당 고유 후보 최대 24개의 건수 제한을 적용하며,
중간 단계에서 바이트 예산으로 자르지 않습니다. 이후 선택한 힌트는 최대 3개이며,
상태·진단·원본 오류까지 포함한 전체 `recall` 객체에 최종 3,600 UTF-8 바이트 제한을
한 번 적용합니다. 자동 응답의 원본 오류 상세는 예산에 맞춰 생략할 수 있으며 생략
건수를 제공합니다. 남은 힌트는 노트 전체, 기억 ID/revision, 정확한 최상위 `source_db`,
원본 `source.run_id`를 보존하며 item 원본이면 `source.item_id`, RUN만 원본이면
archive 포인터도 보존합니다. 일치 단서는 최대 1개만 포함합니다. 중복된 중첩 DB 필드와 item 원본의
불필요한 archive 메타데이터는 생략합니다. 수동 `tapl_recall`, `tapl_get_memory`,
Viewer 조회는 전체 메모리 필드·페이지네이션·원본 오류를 유지합니다.

간결한 진단은 적격 일치 건수(`matched_count`)와 실제 반환 힌트 수(`injected_count`)를
구분하며, 공간이 허용되면 예산 제외 상세도 포함합니다. 회상 이벤트에는 범위가 제한된
단계별 건수,
응답 바이트/상한, 규칙 정보를 보존하며 원본 프롬프트나 대화는 저장하지 않습니다.
측정값이 없는 과거 이벤트는 알 수 없는 값이며 일치·제외 건수 0으로 해석하지 않습니다.
기존 SQLite의 FTS를 사용하므로 임베딩, 추가 모델 호출, 상주 프로세스가 필요하지
않습니다. 상한은 내부 값이며 새 설정이나 CLI 인자는 없습니다.

강화는 RUN당 최대 한 번이며 마지막 내용 수정이나 강화 후 24시간이 지나야 합니다.
오래됐다는 이유만으로 관련 기억을 삭제하거나 제외하지 않습니다.

회상과 원문 조회는 같은 작업 폴더의 여러 DB를 참조합니다. 결과의 `source_db`를 상세 조회와 `memory_uses`에도 전달하세요. 다른 환경의 기억은 읽기 전용이며 변경·삭제·강화를 수행하지 않습니다. [공유 이력의 원본 구분](storage.ko.md)을 참고하세요.

## Agent 조회 기록

Agent의 성공한 메모리·히스토리 검색과 원문 조회는 호출자가 소유한 기존 활성 RUN에 간결한 포인터를 기록합니다. 자동 회상은 응답 예산 안에서 반환한 힌트만 기록합니다. Viewer에서는 검색 결과에 **찾음**, 원문 상세 응답에 **원문 확인**, 명시적으로 재사용한 근거에 **작업에 사용**을 표시합니다. RUN·아카이브 조회는 루트만 기록하며 하위 항목을 개별 조회한 것으로 간주하지 않습니다. 메모리 상세는 원문 내용이 반환됐을 때만 출처를 확인한 것으로 기록합니다.

조회 추적은 응답 후 같은 소유 RUN인지 다시 확인합니다. DB를 생성하거나 다른 출처에 쓰지 않으며 Viewer 탐색과 실패한 조회는 제외합니다. 기록할 수 없어도 성공한 조회를 실패로 바꾸지 않습니다. 과거의 미기록 조회는 재구성하지 않습니다. 출처 포인터와 최대 160자의 표시 제목만 보존하며 검색어·대화 원문·원본 본문을 복제하지 않습니다.

보유한 정보를 실제로 사용할 때는 현재 RUN과 정확한 hook 세션으로 `tapl_use_references`를 호출합니다. 같은 대화 세션의 이전 RUN에서 원문을 확인한 자료는 다시 조회하지 않아도 됩니다. 기억은 실제 반환된 노트(수동 회상·예산 안에 남은 자동 회상·상세 응답)와 일치하는 원문 확인 근거가 모두 필요합니다. 검색·목록 노출, 다른 세션의 조회, 폐기된 조회 RUN은 근거가 되지 않습니다. 제출한 대상과 사용한 기억의 정확한 원문만 추가하며 다른 과거 조회는 따라오지 않습니다. 인자와 예시는 [MCP 사용 계약](../reference/mcp.ko.md#이력과-메모리)을 참고하세요.

식별 키는 종류·원본 DB·대상 유형·정확한 ID입니다. 반복 사용은 현재 RUN의 기존 카드와 선을 재사용하고 상태만 승격하며 첫 사용 설명을 유지합니다. 나중에 조회 결과가 다시 와도 **작업에 사용** 상태는 낮아지지 않습니다. 그래프 사용 기록은 기억 저장·강화와 별개입니다. 자동 회상을 꺼도 명시적 사용은 가능하며, 활성화된 완료 시 `memory_uses` 처리도 같은 연결을 최선 노력으로 시도합니다. 다른 DB 또는 강화 대기 시간으로 강화를 건너뛰어도 유효한 사용 연결은 남을 수 있습니다.

현재 그래프는 참조 ID를 최대 200개 보존하며 사용 근거를 조회 관찰보다 우선합니다. 조회 관찰은 기존 상한·교체 규칙을 유지합니다. 명시적 사용은 기억의 정확한 원문을 포함해 고유 사용 ID 200개를 넘을 수 없습니다. 초과 배치는 전체 거절하고 기존 사용 항목을 유지합니다. snapshot은 인덱스에서 상태 이벤트를 최대 3행 읽습니다. 과거 근거 조회는 같은 세션의 보존된 조회 이벤트를 순회할 수 있으며 임의의 나이·이벤트 수로 자르지 않습니다. [현재 RUN 마인드맵](viewer.ko.md#viewer-탐색)은 이 출처별 관계를 표시합니다.

## 저장할 때 키워드 재사용

기억을 저장하거나 키워드를 수정하기 전에 `tapl_list_memory_cues`를 조회하고,
의미가 같은 기존 표현을 선택합니다. 같은 대화에서 이미 확인한 표현은 다시 조회하지
않고 재사용할 수 있습니다. 적절한 항목이 없는 새 개념만 새 표현을 추가합니다.
의미 판단은 에이전트가 하며 별도 모델 호출이나 고정 동의어 사전은 추가하지 않습니다.

```json
{"session_id":"<current-hook-session-id>","query":"자산목록","limit":20,"offset":0}
```

읽기 전용 응답은 `cues: [{"cue":"자산 목록","usage_count":2}]`, `total`, 페이지
인자와 `source_db`를 제공합니다. 각 항목은 대표 표현이며 별칭 배열은 없습니다.
빈 `query`는 사용 건수 0인 항목을 포함한 대표 표현 목록을 조회합니다. `limit`은
1–50개(기본 20), `offset`은 0 이상, `query`는 최대 200자입니다. 대표 표현과 보존된
별칭을 문자 그대로 검색하고 공백 차이도 제안하며, 같은 대표 표현은 한 번만 반환합니다.
정규화한 정확 일치, 공백 차이 일치, 나머지 부분 일치 순이며 같은 조건에서는 사용 건수와
고정된 표현 순서로 정렬합니다. 다른 표현으로 찾지 못하면 페이지를 넘기거나 전체 목록을
확인하세요. 기본값은 모든 이력을 합친 목록이 아닌 로컬 쓰기 DB의 목록입니다. 정확한
`source_db`로 다른 DB의 목록도 읽기 전용 조회할 수 있습니다.

조회한 표현들이 같은 개념임을 확인하면 에이전트는 이 작업 중
`tapl_merge_memory_cues`를 호출할 수 있으며 병합마다 사용자에게 재확인을 받지 않습니다.
기존 `target_cue` 하나와 흡수할 기존 표현 1–20개를 `cues`로 지정합니다. 두 인자 모두
보존된 별칭을 허용하며 대상은 해당 대표 표현으로 해석합니다. 예를 들어 두 표현을
조회해 같은 의미임을 확인한 뒤 다음과 같이 호출합니다.

```javascript
await call("tapl_merge_memory_cues", {
  session_id: "<current-hook-session-id>",
  target_cue: "자산 목록",
  cues: ["자산목록"]
});
```

병합은 로컬 쓰기 DB에서만 가능합니다. 선택적 `source_db`는 해당 원본의 정확한
파일명이어야 하며 다른 DB는 거절합니다. TAPL은 유사도만으로 자동 병합하지 않습니다.
목록 정의와 기억 연결을 합치고 흡수된 표현은 별칭으로 보존하며 반복 호출은 중복되지
않습니다. 간결한 응답은 `target_cue`, `merged_cues`, `affected_memories`,
`status`(`merged` 또는 `unchanged`)를 제공합니다. 기존 기억의 본문·저장된 cue JSON·
지문·revision·시각·원본·FTS는 그대로 유지하므로 기존 기억 검색 결과도 바뀌지 않습니다.
목록 별칭으로 회상 질의를 확장하지 않습니다.

새 저장과 명시적인 키워드 수정은 보존된 별칭과 NFKC·대소문자 무시·연속 공백 정리 후
같은 항목을 대표 표현으로 해석합니다. 나머지 새 표현은 기억 저장과 같은 트랜잭션이
성공할 때만 등록합니다. `자산목록`과 `자산 목록`은 에이전트가 기존 표현을 재사용하거나
병합할 때까지 별개로 남습니다. 선택한 키워드가 대표 표현으로 해석된 뒤 중복되거나
고유 개념이 3개 미만이면 쓰기를 거절하므로 다른 구체적인 개념을 선택해 재시도하세요.
잘못된 입력·충돌·중복·재시도로 실패하거나 중복된 저장은 불필요한 키워드나 연결을
남기지 않습니다.

사용 건수는 삭제되지 않은 활성·대체된 기억을 대표 표현마다 한 번씩 셉니다. 한 기억의
기존 키워드 여러 개가 병합되어도 중복 계산하지 않습니다. 기억을 삭제하면 연결을 제거하고
대표 표현은 사용 건수 0으로 보존해 재사용합니다. 목록 초기화도 기존 기억과 검색 색인을
유지합니다. 본문만 수정할 때도 기존 키워드 문자열을 유지합니다. 목록 조회는 기억 내용이나
원본을 읽었다는 증거가 아니며 마인드맵 조회 기록도 만들지 않습니다. 일반 도구 응답마다
전체 목록을 붙이지 않습니다.

## 완료 시 기억 검토

`tapl_finish_run`의 선택 필드 `memory_candidates`, `memory_uses`,
`memory_review={"decision":"capture"|"skip","reason":"..."}`로 기억 저장과
검토 결정을 기록합니다. 후보는 slot 1 또는 2, cue 3–5개, 240자 이하 note,
`source_run_id`와 선택적 `source_item_id`를 가집니다. 짧은 1–2문장은 권장사항이며
검증 조건이 아닙니다. 약어·버전·소수·문장부호도 사용할 수 있습니다.
검증한 함정이나 재사용할 결정처럼 원본 근거가 있는 교훈만 저장하고, 일반 완료 요약,
비밀값, 원문 덤프, 추측은 제외합니다. 사용 기록에는 memory ID와 revision,
`source_checked=true`, 구체적인 `usage`가 필요합니다. 단순 노출은 사용이 아닙니다.
기억 인자를 하나라도 전달할 때 `expected_run_id`를 반드시 지정합니다.

회상이 활성화된 run은 완료할 때 기억을 검토합니다. 후보를 전달하면 `capture` 결정으로
간주합니다. 남길 교훈이 없다면 `memory_review={"decision":"skip",
"reason":"완료 기록 외에 재사용할 교훈이 없음"}`을 전달합니다. skip에는 비어 있지 않은
240자 이하 사유가 필요합니다. 후보와 결정을 모두 생략하면 `review_required`가 남습니다.
작업 완료가 기억 저장 성공을 의미하지는 않습니다.

사용자에게 보여 줄 최종 결과는 기억 처리보다 먼저 저장되므로 기억 오류가 완료 기록을
되돌리지 않습니다. 간결한 응답도 `active_run`만 추출하지 말고 `recall`, `memory`를
포함한 전체 내용을 확인합니다. `tapl_finish_run` → 응답의 기억 처리 결과·다음 행동 확인
→ `tapl_finish_archive` 순서로 실행합니다. 반환된 권고를 재사용하며, 필요한 상세 정보가
없거나 응답 오류·잘림, 컨텍스트 유실, 외부 상태 변경 가능성이 있을 때만 status/next를
추가 조회합니다.
status와 next-action의 `memory_review`에는 `status`, `decision`, `capture_count`,
`pending_errors`가 담깁니다. 결정과 미해결 오류는 기존 run 이벤트에 남아 재시도와
프로세스 재시작 후에도 유지됩니다. 실패한 후보를 수정해 같은 run/slot으로 한 번
재시도하거나 사유와 함께 명시적으로 skip합니다. 성공한 slot을 다시 보내거나 잘못된
입력을 그대로 반복하지 않습니다. 새 검토 기록이 생긴 run은 미해결 검토를 해소한 뒤
보관합니다. 기억 검토 이벤트가 없는 이전 run은 계속 보관할 수 있고 회상이 비활성화된
run은 검토 대상에서 제외됩니다. 보관된 run의 재시도가 다음 run을 수정하지 못하도록
검사합니다.

내용 수정은 신선도를 초기화하며, 검증된 재사용은 내용 수정 시각을 바꾸지 않고
반감기를 7일에서 최대 90일까지 늘릴 수 있습니다. 같은 run에서는 한 번만 강화하며,
직전 내용 수정·강화 후 24시간이 지나야 합니다. 오래된 기억도 관련성이 높으면 회상할 수
있고, 시간이 지났다는 이유로 삭제하지 않습니다.

## Viewer에서 기억 읽기

웹·VS Code 공통 Viewer는 **워크스페이스를 중심**으로 원문·기억·공유 단서를 사방으로 연결합니다. 중심은 연결된 DB를 포함한 현재 워크스페이스의 결과 모음을 나타내며 출처의 실제 소유 관계를 바꾸지 않습니다. 실제 기록된 출처와 정규화 후 같은 단서만 연결하며, 현재 검색 결과 페이지의 관계를 보여 줍니다. 유사성을 추론하거나 전체 저장 목록을 한꺼번에 그리지 않습니다. 공유 단서는 여러 기억으로 연결되고 검색에 일치한 단서는 강조합니다. 기억은 상세, 원문은 원본 기록·RUN, 단서는 첫 페이지부터 검색을 엽니다. 검색·페이지 이동·전체 저장 수와 일치 수·저장 진단도 유지합니다.

드래그·두 손가락 스크롤은 양축 이동, 핀치·Ctrl+휠은 확대·축소입니다. 이동 제한·키보드·포인터 모션·동작 줄이기는 [RUN 마인드맵](viewer.ko.md#viewer-탐색)과 같습니다. 상세에서 돌아오면 같은 Viewer 세션의 워크스페이스·검색·페이지별 카메라를 복원합니다. 중심 워크스페이스나 중앙으로 버튼으로 원점에 돌아옵니다. 카드는 회전하지 않으며 결과가 많아도 서로 겹치지 않게 배치합니다.

상세는 기억·원본 미리보기와 속성을 분리하며 기록이나 RUN 원본을 열 때 원본 DB를 유지합니다. 회상 강도는 반올림한 백분율로 표시하고 정확한 저장 값은 추가 필드에서 확인합니다. 이는 떠올리기 쉬운 정도이며 정확성에 대한 신뢰도가 아닙니다. 구조화된 원본 데이터는 펼칠 수 있는 수직 필드로 읽습니다. [Viewer 상세](viewer.ko.md#상세와-구조화된-필드-읽기)를 참고하세요.

## 조회·수정·삭제

웹·VS Code가 공유하는 Viewer는 기억 목록/검색, 상세, 원본을 읽기 전용으로 제공합니다.
**저장된 기억 수**와 **검색과 일치한 기억 수**를 구분하고 최근 기억 저장 실패가 있으면 표시합니다.
실패는 명시적 skip 이후에도 남는 과거 진단 기록이므로, 미해결 여부는 해당 run의 현재
검토 상태로 확인합니다. 진단 정보를 제공하지 않는 이전 host도 기존 기억 조회를 유지합니다.
기억 수정/삭제는 사용자에게서 명시적 요청을 받은 Agent가 MCP `tapl_update_memory`,
`tapl_delete_memory`와 현재 `expected_revision`으로 수행합니다. 충돌 시 최신 revision을
확인합니다. 삭제한 기억은 tombstone으로 남으며 회상에서 제외됩니다. `tapl_recall`은
수동 읽기 도구입니다. 추론 그래프, 추가 LLM 호출, 백그라운드 프로세스는 추가하지 않습니다.

## 설정과 업그레이드

```sh
taplctl config set recall.enabled false
taplctl config unset recall.enabled  # 기본값 true 복원
```

비활성화하면 자동 저장·회상·강화가 중단되지만 수동 조회·수정·삭제는 가능합니다.
기억 workflow는 MCP를 사용하며 관리 CLI에 별도 workflow 명령을 추가하지 않습니다.
schema 15는 키워드 목록·별칭 테이블·기억 연결을 추가합니다. 첫 쓰기 업그레이드는 커밋된 WAL 데이터를
포함한 `.tapl/tapl-{UUID}.db.pre-v15.bak` 백업을 한 번 생성하고, 기존 기억과 FTS를
수정하지 않고 키워드와 연결을 초기화합니다. 목록과 스키마 버전은 함께 반영되며 초기화에
실패하면 재시도할 수 있습니다. 읽기 전용 조회는 schema 14·15를 지원합니다. 다른 DB를
포함한 schema 14의 목록은 마이그레이션 없이 기존 키워드에서 도출합니다. 그보다 오래된
DB는 소유자가 먼저 초기화·업데이트해야 합니다.

이전 업그레이드의 백업도 유지합니다. schema 11→12는 검색 색인을 재구축하기 전에
`.tapl/tapl-{UUID}.db.pre-v12.bak`을 생성하고 더 오래된 DB는 `.pre-v11.bak`을
사용합니다. 업그레이드할 때는 실행 중인 TAPL 서버를 종료하고 새 버전으로 다시 시작하세요.
schema 15에서 이전 버전으로 되돌릴 때는 모든 쓰기를 중단하고 이후 작업을 별도로 보존한
뒤, 해당 업그레이드 전 백업과 호환되는 TAPL 버전을 사용합니다. 목록을 삭제하는 역방향
마이그레이션은 제공하지 않습니다.

## MCP 조회 예제

에이전트가 현재 hook의 `session_id`를 넣어 `tapl_recall`에 다음 인자를 전달합니다. 반환된 기억 ID로 `tapl_get_memory`를 호출하고 원본 item/archive를 확인한 뒤 적용합니다.

```json
{"session_id":"<current-hook-session-id>","query":"SQLite rollback","limit":3,"offset":0}
```

수정·삭제는 사용자의 명시적 요청이 있을 때만 수행합니다. 먼저 현재 revision을 읽고 `expected_revision`으로 전달합니다.
