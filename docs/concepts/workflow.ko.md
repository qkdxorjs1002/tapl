# 워크플로

[문서 홈](../README.ko.md) · [English](workflow.md)

TAPL은 요청의 의도, 계획, 승인, 실행, 근거와 결과를 작업 공간 DB에 보존합니다. 사용자는 평소처럼 결과를 요청하고 Codex가 MCP로 기록을 관리합니다. 요청에 맞춰 흐름이 달라지므로 모든 답변에 같은 개수의 기록이 필요한 것은 아닙니다.

## 수명주기에서 각 기록의 역할

| 기록·단계 | 목적 |
| --- | --- |
| RUN | 요청·분류·세션·최종 결과 소유 |
| HISTORY | 관련 이전 작업을 찾고 원본 근거 확인 |
| PLAN | 한 주제의 요구사항·접근·범위·검증 설명 |
| APPROVAL | 사용자의 실행 결정과 승인 범위 보존 |
| TASK | 구체적 실행·의존성·검증·차단 사유 추적 |
| FINDING | 사실과 그 사실이 의사결정에 미친 영향 보존 |
| ARCHIVE | 정리한 결과를 다음 작업에서도 사용하도록 보관 |

일반적인 계획형 요청은 RUN과 HISTORY에서 PLAN, 승인된 TASK 실행, 검증, 결과 기록, ARCHIVE로 이어집니다. 의사결정에 영향을 주는 근거가 나타나면 어느 단계에서든 발견 사항을 추가할 수 있습니다. 이 이름은 고정된 도구 호출 순서보다 각 단계의 책임을 설명합니다. 저장 필드는 [기록 구조와 메타데이터](records.ko.md)를 참고하세요.

## 작업 종류·엄격도·기록 모드

Agent는 요청 결과를 `answer`, `investigation`, `analysis`, `planning`, `implementation`, `mixed`로 분류하고 별도로 엄격도를 선택합니다.

| 모드 | 선택 기준 | 계획 깊이 |
| --- | --- | --- |
| Fast | 모든 차원이 낮다고 확인됨: 한 목적·표면, 되돌릴 수 있는 작업, 한 검증, 닫힌 경계. 구현은 최대 두 파일 | 영구 변경에는 간단한 실행 계획 |
| Standard | Fast나 Strict에 해당하지 않는 작업 | 간결한 실행 계획 |
| Strict | 보안·개인정보·권한, 스키마·파괴적 작업, 공개 호환성, 배포·외부 쓰기, 장애·데이터 정합성, 비가역 영향, 근거 충돌 | 위험·인터페이스·복구·검증 경계 |

알려지지 않은 사항이 있으면 Fast로 분류하지 않습니다. 작업 공간에 따라 확인이 필요한 사항은 분류 전에 제한된 읽기 전용 탐색으로 확인할 수 있습니다. Root와 helper 전체를 합쳐 로컬 대상 조회 최대 세 번이며 수정이나 테스트는 하지 않습니다. 이후 범위·위험·불확실성이 커지면 분류를 상향해야 합니다.

기록 모드는 직접 선택하지 않고 TAPL이 도출합니다.

- **Lightweight:** Fast의 비영구 Answer/Investigation/Analysis/Planning. PLAN·TASK 기록이 필요 없습니다.
- **Planned:** 영구 변경과 모든 Standard/Strict 요청. 명시적 PLAN·TASK로 실행을 관리합니다.

계획을 만들면 작업 종류·엄격도를 바꾸지 않고 lightweight를 planned로 승격할 수 있습니다. 작성 상세도(`precise`, `normal`, `minimal`)는 기록 분량과 Task 묶음을 바꾸며 엄격도·승인·필수 근거·완료 규칙은 바꾸지 않습니다. [작성 상세도](../guides/authoring-detail.ko.md)를 참고하세요.

## 한 요청의 여러 주제

기본값은 하나의 RUN입니다. 독립 주제는 요청 순서대로 별도 계획을 사용합니다. 예를 들어 파서 수정은 `PLAN-001`, 무관한 Viewer 개선은 `PLAN-002`입니다. Task를 설계하기 전에 주제별 요구사항·접근·검증을 작성합니다. Task의 `spec_id`는 해당 주제의 계획을 가리킵니다.

한 결과를 위한 단계·예제·제약·테스트는 한 계획에 둡니다. 한 기능을 위한 독립 수정 두 개는 그 계획 안의 별도 Task가 될 수 있습니다. 별도 RUN 수명주기는 명시적으로 요청했을 때만 사용하며, 분리 대기열은 요청한 순서나 앞 결과를 소비하는 의존성을 표현할 수 있습니다.

일반적으로 하나의 RUN에 두 계획을 만들며 수정 파일마다 계획을 만들지 않습니다. 주제별 작업 종류가 다르면 RUN은 Mixed로 분류하고 가장 높은 주제 엄격도를 사용합니다.

## 승인과 실행

계획은 구현보다 먼저입니다. Agent는 중요한 범위·호환성·인터페이스·선택 문제를 해소하고 명시적 사용자 확인을 받은 뒤 계획을 확정합니다. 계획 확정 확인과 실행 승인은 목적이 다릅니다. 수정·구현·검증·테스트를 명시적으로 요청하면 이미 그 범위의 실행 승인으로 취급하며 TAPL에 기록합니다. 승인은 요청 범위를 넓히거나 무관한 변경을 허용하지 않습니다.

순차 실행은 의존성이 완료된 Task를 작업 직전에 시작하고, 다음 Task를 시작하기 전에 정리합니다.

| 상태 | 의미 |
| --- | --- |
| Pending | 설계했지만 아직 시작하지 않은 작업 |
| In Progress | 실제 실행 중인 작업 |
| Completed | 구현과 필수 검증이 완료된 작업 |
| Blocked | 진행할 수 없어 차단 사유와 구체적인 다음 행동을 남긴 작업 |
| Skipped | 의도적으로 제외했거나 대체되어 이유를 보존한 작업 |

검증하지 않은 작업을 완료로 표시하지 않습니다. Task 묶음은 설정한 작성 상세도와 작업의 위험·의존성·소유권에 따라 정합니다.

병렬 실행은 원자적 batch dispatch를 사용합니다. 대상 Task는 같은 계획·병렬 그룹에 속하고 실제 SubAgent 실행자를 사용하며 의존성이 완료되고 독점 경로를 가져야 합니다. Root가 dispatch manifest를 확인하고 실제 Agent를 시작하며 정확한 `execution_id`로 각 실행을 정리합니다. 중단되었거나 시작하지 못한 batch는 재시도 전에 복구·취소해야 합니다. DB의 batch만으로 외부 Agent가 실행되거나 종료되지는 않습니다. [SubAgent](../guides/subagents.ko.md)를 참고하세요.

## 작업 공간과 세션 경계

Codex 작업 폴더 자체가 `.tapl/tapl.db`를 소유합니다. TAPL은 상위 DB·Git 루트·저장소 표식을 탐색하지 않습니다. `repo/packages/app`의 세션은 `repo/.tapl/tapl.db`가 있어도 `repo/packages/app/.tapl/tapl.db`를 사용합니다. 기존 DB를 이동하거나 합치지 않습니다.

Hook 이벤트에는 존재하는 절대 경로 `cwd`가 필요하며 MCP 서버는 실행 중 시작 작업 폴더에 고정됩니다. Hook DB 재정의는 그 폴더의 DB를 가리켜야 합니다. 관리 CLI는 명시적 DB·작업 공간 선택을 제공합니다. [CLI 참조](../reference/cli.ko.md)를 참고하세요.

모든 MCP 호출에 Codex hook의 `session_id`를 전달해야 합니다. 각 세션은 자신의 RUN·승인·Task·분리 대기열·Stop 처리·아카이브 수명주기를 소유합니다. 같은 세션을 재개하면 그 RUN을 이어가고 새 세션은 다른 세션의 작업을 인수하지 않습니다. 생략하면 격리된 legacy 범위를 선택하며 세션 소유 기록이 생기면 식별자 없는 쓰기는 거부합니다. 기존 세션 미분리 기록은 legacy에 남고 스키마 갱신 전 `.tapl/tapl.db.pre-v14.bak`을 보존합니다.

이력은 작업 공간 전체에서 검색할 수 있지만 활성 워크플로 소유권은 세션별입니다. 작업 파일은 공유하므로 같은 파일의 동시 수정은 조율하거나 별도 worktree를 사용하세요. 세션 소유권과 batch 경로 검사는 파일 시스템 격리가 아닙니다.

## 검증과 종료

Agent는 계획의 검증 기준으로 Task 결과를 확인하고 `tapl_finish_run`으로 최종 결과를 기록하며, 기억 후보를 검토하거나 이유와 함께 수집을 생략합니다. 완료 응답을 확인해 미해결 기억 오류를 처리한 뒤 `tapl_finish_archive`를 호출합니다. 작업 결과는 기억 처리와 별도로 저장합니다. [연상 기억](../guides/memory.ko.md)을 참고하세요.

대기·차단·생략·미검증 작업을 완료로 주장하지 말고 기록에 드러냅니다. 실행할 작업을 정리했거나 RUN이 대체·노후화되었거나 사용자가 아카이브·폐기를 명시적으로 선택하면 아카이브합니다. 계획만 요청한 경우 실행이나 종료를 선택할 때까지 활성 상태를 유지합니다.

`observe` hook은 워크플로 문제를 안내하고 `enforce` hook은 필수 상태 누락·미완료 Task·활성 batch 때문에 영구 변경 도구나 Stop을 차단할 수 있습니다. Hook 설정은 Fast/Standard/Strict와 별개입니다. Viewer는 검증 상태를 표시하고 명시적 확인을 거친 RUN 폐기를 제공하지만 코드의 정확성을 검증하지는 않습니다. [연결](../getting-started/integrations.ko.md)과 [Viewer](../guides/viewer.ko.md)를 참고하세요.

첫 실행은 [빠른 시작](../getting-started/quickstart.ko.md), 정확한 수명주기 인자와 검증 도구는 [MCP 참조](../reference/mcp.ko.md)를 참고하세요.
