검증 방법

실제 대화는 morae-mcp/libkrun, Codex CLI 0.153.4, `gpt-6-astra/high`로 실행했다. 조건과 반복마다 새 Box, git fixture, TAPL DB·설정과 Codex 세션을 사용한다. 호스트에서 실제 대화 테스트를 실행하지 않는다. 네트워크 relay를 공유하므로 대화 VM은 순차 실행하고, 오프라인 전체 테스트는 독립 VM에서 실행한다.

기존 6조건(수정, 기억 활성화, 계획 전용, 재개, 병렬 위임, 독립 주제)에 읽기 전용과 관찰 helper 조건을 추가했다. 읽기 전용 조건은 파일·다른 산출물 미변경, Fast 분류, plan/task/실행 승인 없이 완료·아카이브, 실제 오타 보고를 검증한다. 계획 전용은 수정·실행 승인·완료·아카이브가 없고 active로 남는지 확인한다.

관찰 helper는 허용된 모델·effort로 실제 자식 1개를 실행하고 `fork_turns=none`을 쓰는지 확인한다. 별도 task/batch 없이 읽기만 수행하는지, 성공한 문서 조회 증거와 완료 결과가 있는지 검사하고 실제 조회 범위·횟수를 수동 검토한다. 상태 쓰기, 편집, 테스트, 중첩 위임, 실패한 조회를 거부하는 평가기 테스트를 포함한다.

병렬 위임은 실제 spawn receipt와 child session을 연결한다. 담당 파일과 task/execution 관계, 성공한 편집·검증 명령, child 완료 후 정확한 execution_id 정산, 실행 구간 중첩과 root만 TAPL 상태를 쓰는지 검사한다. 독립 주제는 파일별 PLAN과 TASK spec_id 연결까지 검사한다. 원본 DB와 rollout의 재검증도 수행한다.

옵션 검사는 `검색 4종 × recall on/off × 위임 5상태 × profile 3종 = 120조합`이다. 각 조합은 별도 workspace·DB·config를 사용하며, 전체 행렬을 새 VM 세 곳에서 반복한다. 전체 정책·현재 설정, retained/stale revision, 불완전 catalog, status 상세·events 옵션을 포함한다. 실제 대화의 recall 조건은 빈 기억 저장소의 이유 있는 skip 경로다. 기억 검색·수정·강화 등 나머지 경로는 기존 자동 테스트가 담당한다.

수정·재검증 과정

읽기 전용 문구 리뷰에서 네 의미 변화를 찾아 수정했다. 갱신 조건의 `only`로 별도 설정 점검을 막을 여지, metadata를 canonical 객체로만 한정할 여지, 기억 후보 제출의 capture 의미 누락, 재탐색 금지를 지나치게 강화한 표현이다. 뒤이어 Stop의 무조건 재질문 지침을 발견해 계획 전용 분기와 맞췄다. 마지막 문구 수정 이후 동일한 제품 코드로 전체 회귀와 실제 대화 반복을 검증했다.

관찰 helper의 첫 파일럿은 전체 MCP envelope를 출력해 응답이 잘렸고 정책을 재조회했다. 원본 rollout에서 잘림 경고를 확인했으므로 재조회 자체는 정책에 맞는 복구다. 다만 첫 중복 출력은 불필요한 컨텍스트 비용이므로, `structuredContent`만 출력하라는 기존 지침을 초기 진입 안내 맨 앞으로 이동하고 developer 진입 훅에도 짧게 명시했다. 합법적인 재조회 조건은 유지했으며 수정 후에는 새 VM으로 반복을 다시 시작했다. 이 파일럿은 최종 통과 집계에서 제외한다.

최종 helper 첫 실행의 판정기는 `Promise.allSettled`의 `fulfilled.value.exit_code`를 읽지 못했다. 원본 명령과 성공 receipt를 확인하고 판정기를 수정해 보존한 증거를 재검사했다. 원본 `result.json`은 덮어쓰지 않고 별도 `review.json`에 판정 수정과 원본 해시를 남겼다. 혼합 응답에서 rejected 또는 exit code 없는 결과를 성공한 조회로 가리는 경우도 거부하도록 음성검사를 보강했다. 판정기는 일반적인 셸 부작용 분석기가 아니므로 helper 세션의 실제 명령·조회 예산·분류 시점·history 미사용도 별도로 검토한다.

독립 주제 판정도 실제 수정 대상이 `action`에 적혔지만 파일명을 반복하지 않은 작업을 잘못 거부했다. 이 fixture의 구체적인 수정 대상(`transactoin`/`transaction`, `indent_size`)도 인정하도록 보강하고 원본 기록을 별도 review로 재판정했다. PLAN별 고유 파일과 TASK의 `spec_id` 연결 검사는 유지했으며 잘못된 PLAN 연결은 계속 실패한다. 이 두 판정기 수정에서는 제품 프롬프트를 바꾸지 않았다.

기존 문장 전체를 비교하던 계약 테스트는 대응하는 새 표현으로 갱신했고 기존 제한 검사는 유지했다. 전체 정책과 Stop이 명시적 계획 전용 요청을 같은 방식으로 처리하는 회귀 검사도 추가했다. 환경 준비 중 누락된 editable build 의존성을 설치했으며, 환경 오류를 제품 통과 표본으로 계산하지 않는다.
